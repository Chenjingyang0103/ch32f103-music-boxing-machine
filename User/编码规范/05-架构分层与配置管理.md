# 5. 架构分层与配置管理

> 模块依赖方向，以及参数、设备号的集中管理方式。

## 5.1 分层结构

`User/` 下自研模块按三层组织，另设公共层供各层共享：

```text
User/
├── App/         应用层    GameLogic / KeyCal
├── Middleware/  中间件层  Filter / Weight / Calibration / PunchDetect / FilterTest
├── Device/      设备层    HCT6521 / SM16028E / Led / Key / MyFlash / Timer / MyRTC
└── Common/      公共层    Project_Config.h
```

依赖方向（逐层单向，禁止反向）：

```text
APP  →  Middleware  →  Device  →  （ch32f10x 库 / debug）
  └───────────┴──────────┴────────→  Common（Project_Config.h）
```

- **正向依赖**：`App → Middleware → Device`；各层均可直接依赖 `Common`。
- **APP → Device 白名单例外**：`GameLogic` 允许直接调用三个平台服务——
  `Led`（靶子指示）、`SM16028E`（显示）、`Timer`（时基）；
  白名单之外的 APP 跨层直调 Device 一律禁止。
- **禁止反向包含**：`Device → Middleware/APP`、`Middleware → APP` 等任何反向依赖
  （含「只是 `#include` 却未调用」的情形）都不允许。
- **装配根**：`main.c` 是唯一的装配根，允许跨层调用所有模块做初始化，但内部不得写业务逻辑。

## 5.2 模块内部状态

- 每个模块内部状态用 `static` 数组按通道保存，`DevNum` 为索引：

```c
static AdcDeviceParamTypedef AdcDeviceParam[ADC_DEV_NUM];
```

- 模块初始化分两步：先填“静态参数”局部结构体，再 `memcpy` 进静态数组：

```c
AdcStaticParamTypedef StaticInit;
StaticInit.SckPort = GPIOA;
StaticInit.SckPin  = GPIO_Pin_12;
StaticInit.SdoPort = GPIOA;
StaticInit.SdoPin  = GPIO_Pin_11;
AdcDeviceStaticInit(&StaticInit, AdcDevNum4);
```

## 5.3 参数集中管理

- 所有模块的可调阈值以 `#define` 汇总到 `Project_Config.h`，按模块分区并标注单位：

```c
/* ==================== PunchDetect 参数配置 ==================== */
#define TRIGGER_THRESHOLD           200     // 开始追踪的门槛（重量 g）
#define RELEASE_THRESHOLD           150     // 松手复位门槛（重量 g）
#define RELEASE_COUNT               2       // 释放计数：连续 N 点低于释放阈值判定松手
```

- 设备号枚举**全局唯一**，定义在 `Project_Config.h`，各模块不再自建：

```c
typedef enum
{
    AdcDevNum0 = 0,
    AdcDevNum1,
    ...
    // 如果后续拓展，直接在此添加，但必须保证数量 <= ADC_DEV_NUM
} AdcDevNumTypedef;
```

- 功能开关用 `0/1` 宏控制，并在注释中说明开 / 关行为：

```c
#define GAME_TIMEOUT_ENABLE         1       // 是否开启超时切换：1=开启，0=关闭
#define GAME_SWITCH_AFTER_HIT       1       // 击打后是否立即切换下一个靶子：1=立即切换，0=等待超时后再切换
```

## 5.5 通道映射与标定数据绑定

`AdcDevNum` 是全工程的索引，把「引脚 → 采集 → 滤波 → 重量 → 标定表 → 靶子 → LED」一路串起来。
因此**改动任一通道的引脚归属时，必须同步改下面三处**，否则数据会整体错位：

| 位置 | 文件 | 说明 |
| --- | --- | --- |
| 引脚定义 | `User/Device/HCT6521.c` → `HCT6521_Init` | 每路 SCK / SDO 的 Port 与 Pin |
| 标定默认表 | `User/Middleware/Calibration.c` → `s_defaultCal` / `s_defaultRate` | 数组第 N 行 / 第 N 项即 `AdcDevNum(N)` |
| Flash 魔数 | `User/Device/MyFlash.h` → `MYFLASH_MAGIC` | 标定表存 Flash，引脚与通道的对应关系变了必须换魔数 |

若换了某通道的引脚归属，就必须按此清单逐条同步；只改引脚而不换魔数的话，
旧 Flash 里的标定数据会被误判为「有效」而错位加载（见 [8.1 Flash 持久化](08-持久化调试与整改建议.md#81-flash-持久化)）。

**扩靶子数量（`GAME_TARGET_NUM`）的连锁**：

- 靶子号 ↔ 通道 ↔ LED 是直接对应的：`GameLogic.c` 中
  `Punch_IsHit((AdcDevNumTypedef)pRun->TargetNum)`、`Led_Off((LedDevNumTypedef)pRun->TargetNum)`，
  即靶子 N ↔ `AdcDevNum(N)` ↔ `LedDevNum(N)`。故 `GAME_TARGET_NUM`、`ADC_DEV_NUM`、`LED_DEV_NUM` 三者应保持一致。
- 只把 `GAME_TARGET_NUM` 改大（如 4 → 6）：随机选靶、击打检测、LED 指示都会自动覆盖到新靶子，
  **编译与逻辑运行没有问题**；但**按键步进标定把通道写死在 `User/App/KeyCal.c`**
  （由 `main.c` 抽出，`KeyCal_Process((AdcDevNumTypedef)CalDevNum)`），只会标定第 0 路。
  要让其余靶子也能正常称重与判力度，必须补一个标定通道切换入口
  （例如按键循环切换 `0 ~ ADC_DEV_NUM-1`），否则那些通道只有默认标定表，读数不可用。
