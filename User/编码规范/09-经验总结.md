## 一、最容易踩的 6 条（先看这里）

| # | 结论 | 一句话原因 |
| --- | --- | --- |
| 1 | HCT6521 读回的是 **24 位二补码**，必须做符号扩展 | 不扩展时 -1 会变成 16777215，差分直接崩 |
| 2 | **`Weight_Init` 必须先于 `Weight_Update`** | 否则 `Rate` / 标定差值全为 0，`0.0f/0.0f` = **NaN** |
| 3 | Flash 布局变了就**必须换 `MYFLASH_MAGIC`** | 只靠魔数判等识别不了布局变更，会读到 `0xFF` → **NaN** |
| 4 | 改任何一路的**引脚归属**，要同步「引脚 + 标定默认表 + 魔数」三处 | 只改引脚 → 标定数据整体错位 |
| 5 | `SM28_Update` 是**阻塞式**发送，一帧数毫秒占满 CPU | 名字像「刷新一下」，实际是软件 bit-bang |
| 6 | 时间参数一律按 **TIM2 时钟 = 8MHz** 换算，别按 72MHz 估 | 72MHz 配置段根本没执行 |

## 二、运行前提：时钟与时基（实测结论）

本板 HSE / LSE 均未焊接，`system_ch32f10x.c` 里虽仍启用 `SYSCLK_FREQ_72MHz_HSE`，
但 **HSE 等待超时后不是「自动切回内部晶振」，而是压根没切过去**，SYSCLK 保持复位后的 HSI 8MHz。

- `main()` 里 [`SystemCoreClockUpdate()`](../Src/main.c#L35) **必须保留，且必须排在 `Delay_Init()` 之前**。
  它按 RCC 寄存器把 `SystemCoreClock` 重算为 8MHz，`debug.c` 中 `p_us = SystemCoreClock / 8000000 = 1`；
  一旦删除或挪到 `Delay_Init()` 之后，`p_us` 会取到 9，所有 `Delay_Us(n)` 只剩实际 1/9 时长，**HCT6521 位时序失效**。
- APB1 复位默认 HCLK/1，72MHz 配置段未执行 → **TIM2 时基 = 8MHz**。

现存不一致（**待处理**）：[`main.c`](../Src/main.c#L40) 当前是 `Timer2_Init(1000, 8)`，
注释却写「ARR = 999, PSC = 7 定时1Ms中断一次」。8MHz ÷ (8+1) × 1000 ≈ **1.13ms**，
比注释的 1ms 偏大约 13%，会连锁影响 `GAME_TICK_PERIOD_MS`、`TIMEOUT_TIME`、运行时间打印。
要精确 1ms 应用 `Timer2_Init(999, 7)`。

## 三、数据链路与各环节经验

```text
HCT6521_Task（非阻塞状态机，读 24 位）
  → Filter_AdcFilt（双模：动态透传 / 静态中位窗口滤波）
  → Weight_Update（差分 → 分段线性插值 → WeiValue）
  → Weight_GetValue = WeiValue * Rate
  → Punch_Tick / Game_Task / SM28 / Led
```

### 3.1 ADC 采集（HCT6521）

- `HCT6521_Task` 是非阻塞状态机（`Idle → Reading → WaitHigh`），主循环每圈调用一次，
  一次完整读取需要 **3 个循环周期**才返回 1，因此主循环被任何阻塞操作拖慢，都会连带拖慢采样。
- 读到的 24 位必须符号扩展，见下一节。
- 低功耗代码整段以注释保留（约 40 行），里面用的是 `AdcGain_64`，与 `HCT6521_Init` 的 `AdcGain_1` 不一致，
  属于**死代码**，改增益时别被它误导。
- `HCT6521_Init` 按 6 路写引脚参数，但 `AdcDeviceStaticInit` 遇到 `DevNum >= ADC_DEV_NUM` 会**静默 return**，
  超出的配置被无声丢弃 —— 扩靶时若只加引脚配置却没同步 `ADC_DEV_NUM`，不会有任何报错。
- `User/example/HCT6521.c` 是**未加入 Keil 工程**的副本（uvprojx 只编译 `User/Device/HCT6521.c`），
  两份文件的引脚归属**并不一致**（例：`PA12/PA11` 在工程文件里是 `AdcDevNum0`，在示例文件里是 `AdcDevNum4`）。
  改引脚时务必确认改的是 `User/Device/` 下那份。

### 3.2 原始数据解析：24 位二补码必须符号扩展

[`Read24Bit`](../Device/HCT6521.c#L450-L466) 已改为返回 `int32_t` 并做扩展：

```c
value = ((int32_t)buffer[0] << 16) | ((int32_t)buffer[1] << 8) | (int32_t)buffer[2];

/* 24 位二补码符号扩展：bit23 为 1 表示负值，高 8 位补 1 */
if (value & 0x00800000)
    value |= (int32_t)0xFF000000;
```

**这是实测确认过的真实 bug**：不做扩展时负值会变成 1600 万量级（如 -1 → 16777215），
破坏 `DiffValue = AdFilterValue - ZeroAdc`，零点相减得到天文数字。
**连锁要求**：符号扩展改动后，旧零点是用旧规则记录的，必须**重新标定或重新采集零点**，
否则「零点与实时值不同源」，相减照样出错。

### 3.3 滤波（Filter，双模）

- `Filter_AdcFilt` **无论动态还是静态都会先把原始值喂进窗口**，模式只决定取值来源：
  - **动态**：直接 `return RawValue`，保证拳击峰值不被削；
  - **静态**：返回 15 点中位窗口滤波值（档位 1 = 窗口 15 / 取索引 7 起 2 个 / 右移 1 位）。
- 因此从动态切静态时窗口内已是最新历史，**不需要补值、也不需要事后还原**。
- 窗口内为**按值淘汰的排序插入**（与上次均值比较决定插入头部还是尾部），
  这是刻意的实现，**不要改成 FIFO 丢最老写最新**。
- 静态档位由 [`Project_Config.h`](../Common/Project_Config.h#L22) 的 `FILTER_STATIC_DEEP` 控制，
  档位表 `s_filterDeep[][4]` 中累加个数都是 2 的幂，用右移代替除法，避免浮点。

### 3.4 重量换算（Weight）

- `Weight_Update` 是**无状态的纯映射**，没有任何累加/积分逻辑。
  出现「重量逐渐上升」时，**换算链路一定不是元凶**，要去查 ADC 原始读数本身。
- **初始化顺序是硬约束**：`Weight_Init` 负责设置 `WeiCalValue{200,500,1000,2000,4000}`、
  `DiffCalValue(= Cal_GetDiff)`、`Rate(= Cal_GetRate)`；未执行时三者全为 0 → `0.0f / 0.0f` = **NaN**，
  且 **`NaN * 0` 仍是 NaN**，会污染全部通道。
  当前在 `main()` 的开机零点采集循环里调用，顺序正确。
- `Weight_Init` 有防单点除零：`DiffCalValue[i] == 0` 时置 1。
- 模块内部**只存 `ZeroAdc` 和 `DiffValue`**，不直接存最新原始值；
  需要最新滤波 ADC 值时用 `Weight_GetAdcValue() = ZeroAdc + DiffValue` 反推。

### 3.5 标定与 Flash 持久化

- 模式：**魔数 + RAM 镜像 + 整块擦写**。所有 `Set` 只改 RAM 镜像 `buf`，`Save` 才真正擦 Flash。
- 布局（见 [`MyFlash.h`](../Device/MyFlash.h#L19-L38)）：
  `偏移 0 magic(4B)` / `偏移 4 cal(144B = 6×6×4)` / `偏移 148 rate(4B)` / `偏移 152 reserved(104B)`，
  块大小 256B，数据区 `0x0800FC00`。
- **魔数必须与布局绑定**：`ADC_DEV_NUM`、`ADC_CAL_POINTS` 或结构体布局一变，
  必须换一个该板**历史上从未用过**的魔数，强制走重写分支。
  仅靠魔数精确判等识别不了布局变更：旧数据被误判「有效」直接加载，
  新布局去读偏移已变的 `rate` 字段，落到 `memset` 填的 `0xFF`，按 IEEE754 解释就是 **NaN**。
  - 魔数是**精确 32 位相等**比较，不存在「值相近就容易命中」；撞车只说明该值历史上确实写过 Flash。
  - 当前值 `MYFLASH_MAGIC = 0x12345611`（历史：`0x12345677`）。**改过的值不要再改回去**；
    想恢复默认可直接擦除数据区。
  - 排查手段：`printf("flash magic = 0x%08X\r\n", *(volatile uint32_t *)0x0800FC00);`（放在 `Cal_Init()` 之前）。
- **标定与实时必须同源**：零点、标定表、实时采样要走同一套解码规则（呼应 3.2）。
- **默认参数表必须显式写满全部元素**：
  写成 `static const float s_defaultRate[ADC_DEV_NUM] = {1.0f};` 时，
  只有第 1 个元素是 `1.0f`，其余按 C 规则补 0，而 `Weight_GetValue = WeiValue * Rate`，
  导致**第 2~6 路重量恒为 0**。现 [`Calibration.c`](../Middleware/Calibration.c#L71-L74) 已写满 6 个 `1.0f`。
- `MyFlash_Init` 在 Flash 空白时会把传入的默认值写回 Flash，
  因此**改了代码里的默认值，首次上电不会生效**（要擦除数据区或换魔数才会重写）。
- 标定流程为**按键步进**：依次零点 → 200g → 500g → 1000g → 2000g → 4000g，
  每放好砝码按一次键才标定当前点，第 6 点完成后自动 `Cal_Save` 并退出。
  旧的阻塞式自动循环标定代码以 `#if 0` 包裹保留，不得删除。
  ⚠ 当前标定目标通道写死在 [`main.c`](../Src/main.c#L94) 的 `uint8_t CalDevNum = 0;`，
  **只标定第 0 路**；要标其它通道需改此初值或补通道切换入口。

### 3.6 通道映射与标定数据绑定（改通道必读）

`AdcDevNum` 是把「引脚 → 采集 → 滤波 → 重量 → 标定表 → 靶子 → LED」串起来的全局索引。
**改动任一路的引脚归属，必须同步下面三处**，否则数据整体错位：

| 位置 | 文件 | 说明 |
| --- | --- | --- |
| 引脚定义 | `User/Device/HCT6521.c` → `HCT6521_Init` | 每路 SCK / SDO 的 Port 与 Pin |
| 标定默认表 | `User/Middleware/Calibration.c` → `s_defaultCal` / `s_defaultRate` | 数组第 N 行 / 第 N 项即 `AdcDevNum(N)` |
| Flash 魔数 | `User/Device/MyFlash.h` → `MYFLASH_MAGIC` | 引脚与通道的对应关系变了必须换魔数 |

**扩靶子数量的连锁**：靶子号 ↔ 通道 ↔ LED 是直接对应的
（`Punch_IsHit((AdcDevNumTypedef)TargetNum)`、`Led_Off((LedDevNumTypedef)TargetNum)`），
故 `GAME_TARGET_NUM` / `ADC_DEV_NUM` / `LED_DEV_NUM` 三者应保持一致。
只把 `GAME_TARGET_NUM` 改大，编译与逻辑运行没有问题，但**标定入口仍只覆盖第 0 路**，
其余通道只有默认标定表，读数不可用 —— **扩靶不要只改一个宏**。

### 3.7 拳击检测（PunchDetect）

- 三态流转 `Idle → Confirm → Track → Idle` 逻辑正确；`default` 分支强制回安全态。
- 事件上报为**边沿触发 + 读取即清零**（`Punch_IsHit`），避免重复触发。
- 触发阈值 200g、释放阈值 150g、连续 2 点低于释放阈值判定松手 —— 均为迟滞设计。
- **静态 / 动态双模判据**：连续超触发阈值点数 ≥ `STATIC_CNT_LIMIT` 进入静态模式，
  低于释放阈值则清零计数并退回动态；判据值用**滤波后值**（与输出同源）。
- **`STATIC_CNT_LIMIT` 不能太小**：进入静态的瞬间，窗口中还混有 `15 - STATIC_CNT_LIMIT` 个旧值；
  中位滤波取索引 7、8，阈值偏小时会取到旧值 → 切换瞬间输出**出现凹陷**。
  保证 `STATIC_CNT_LIMIT ≥ 8` 即可让索引 7、8 全部落在加载值区间；取 14 / 15 还能避免短促拳击误进静态。
- **静态稳定值只在模式 0→1 的判定瞬间锁存一次**，之后不再更新，
  以免砝码下降过程中的中间读数覆盖它；该瞬间滤波恰好仍是动态透传，锁存到的是真值。
- **失败方案（已回滚，勿重做）**：曾尝试「三段式静态重量跟随」修复，
  结果放 500g 砝码时称重值持续偏低（200g~450g 区间），已**完全回滚且不得保留任何残留代码或注释**。
- 已知次要问题（用户明确暂缓）：`default` 分支漏清 `HitReported`、`GameLogic` 中冗余的
  `Punch_ClearPeakForce` 调用、`Punch_IsActive` 为无调用死接口、顶部注释死代码、公共接口无 DevNum 边界检查。

### 3.8 游戏逻辑与显示

- 主循环每拍顺序固定：`HCT6521_Task → Filter_AdcFilt → Weight_Update → Punch_Tick`。
  `Filter_AdcFilt` 的模式参数取自 `Punch_GetFilterMode`，而 `Punch_Tick` 在滤波**之后**才更新模式状态，
  所以「动态 ↔ 静态」双向切换都有**固定 1 拍的对称延迟**（当前约 1.13ms/拍，取决于定时器）。
- **每轮选靶后重记零点**：`GameState_Ready` 里用该通道最新滤波 ADC 值 `Weight_SetZero`，
  消除通道零点漂移（对应「放置砝码后重量逐渐上升」）。
  边界：若选靶瞬间该通道仍有残留受力，本轮零点会被抬高，判打变迟钝。
- 显示分工：**静态载显示锁存的稳定读数，动态冲拳显示本回合峰值力度**；
  静态判定发生在松手前，故松手瞬间先把 `FilterMode` 锁存到 `LastFilterMode` 再清除。
- `main.c` 中开机自动执行 `Game_Start()`，按键分支 `KeyNum == 2` 的 `Game_Start()` 已被注释。
- LED 靶子指示：靶子 N ↔ `AdcDevNum(N)` ↔ `LedDevNum(N)`，
  选靶亮 → 击中/超时灭 → 回合结束 `Led_AllOff` 兜底。

### 3.9 阻塞式数码管与主循环占用

- `SM28_Update` 是**同步阻塞**的一帧发送（138 字节全部按位翻转 GPIO，无 DMA、无分片），
  调用期间占满 CPU：8MHz 下用库函数约 **9ms**，改为直接写寄存器后约 **2.5ms**。
  收益来自省掉跨 `.c` 文件、编译器无法内联的函数调用：

```c
    sclPort->BSHR = sclPin;           /* 等价于 GPIO_SetBits(sclPort, sclPin); */
    sclPort->BCR  = sclPin;           /* 等价于 GPIO_ResetBits(sclPort, sclPin); */
```

  寄存器写法位时序完全不变，属零风险提速；替换时旧写法以注释保留便于回退。
- **调用频率直接决定 CPU 占用**：曾放在主循环每圈调用，把主循环周期拉到约 9ms，
  并连带拖慢 `HCT6521_Task`。现已改为两个低频点：
  `main.c` 的秒变化分支（每秒一次）与 `GameLogic.c` 的 `GameState_Result`（每回合一次）。
- 未实施（用户暂缓）：**脏标记 + 限速**（缓冲区没变就不发 + 最短发送间隔）可把总占用从约 30% 降到约 5%，
  但两者都**只降总占用、不降单次阻塞时长**；要压低单次仍需分片状态机或改 SPI/DMA。

## 四、踩坑清单（按现象反查）

| 现象 | 根因 | 规避 / 排查 |
| --- | --- | --- |
| 重量全为 NaN | Flash 布局变了但魔数没换 → 旧数据被误判有效 → 读到 `0xFF` 当 float | 换魔数；先打印 `0x0800FC00` 处魔数确认 |
| 重量 NaN、除零 | `Weight_Init` 未先于 `Weight_Update` 执行 | 保证初始化顺序 |
| 第 2~6 路重量恒为 0 | `s_defaultRate[ADC_DEV_NUM] = {1.0f};` 只初始化了第 1 个 | 默认表显式写满全部元素 |
| 负值变成 1600 万量级 | 24 位补码未符号扩展 | `Read24Bit` 做符号扩展；改规则后重新采零点 |
| 零点与实时相减得天文数字 | 零点用旧规则记录、实时用新规则 | 标定与实时同源；改规则后重新标定 |
| 秤上砝码后重量**逐渐上升** | 与换算逻辑无关（纯映射无状态），是 ADC 原始读数在爬 | 先开 `{AD%d}` 打印看原始值；再查机械蠕变/自热温漂、Σ-Δ 建立时间、采样时序 |
| 定时器节拍偏大约 10~13% | 按 72MHz 估算 / 实际是 8MHz；或 `(1000,8)` 而非 `(999,7)` | 一律按 8MHz 换算 |
| `Delay_Us` 只有 1/9 时长、位时序失效 | `SystemCoreClockUpdate()` 被删或挪到 `Delay_Init()` 之后 | 保持原顺序 |
| 手工新建的 `.c` 不参与编译，调用它即**链接报错** | Keil 把它当文本文件（uvprojx `<FileType>9`） | `.c` 设 `FileType 1`、`.h` 设 `5`；改 uvprojx 前先关 Keil |
| 进静态的瞬间重量**凹陷** | `STATIC_CNT_LIMIT` 太小，中位窗口取到旧值 | 保证 `STATIC_CNT_LIMIT ≥ 8`（现 14） |
| 扩靶后除第 1 路外读数不可用 | 标定入口 `CalDevNum` 写死为 0 | 同步三张表 + 补标定通道切换入口 |
| 静态载称重持续偏低 | 曾用「三段式静态重量跟随」方案 | 该方案已回滚，勿重做 |
| 主循环吞吐变慢、采样变慢 | `SM28_Update` 每圈调用，单次阻塞数毫秒 | 只放在低频点（每秒 / 每回合） |
| 编辑器整文件铺红绿标，但源代码管理面板**无变更文件** | 工作区文件 CRLF、索引为 LF，`core.autocrlf=true` 归一化后内容一致 | 以 `git status` / `git diff` 为准，属**显示误报**，不动 autocrlf、不加 `.gitattributes` |

## 五、排查方法论

1. **先分层定位，再怀疑算法**：链路是 `ADC → 滤波 → 换算 → 检测 → 逻辑 → 显示`，
   用串口分层放宽打印（`{AD%d}` / `{Filt%d}` / `{Wei%d}`），确认异常出现在**哪一层**。
   「重量爬升」的例子说明：换算层无状态就不会产生渐变，问题必然在更上游。
2. **改数据解码规则后，先怀疑历史数据**：零点、标定表存 Flash，规则变了旧值就不同源。
3. **改 `ADC_DEV_NUM` / Flash 结构体布局后，先换魔数**，别指望「看起来一样」。
4. **命名不可信**：`SM28_Update` 名字像轻量刷新，实际阻塞数毫秒 —— 调用前先确认单次耗时。
5. **改 Keil 工程文件前先关 Keil**，否则会被 Keil 内存中的版本覆盖写回。
6. **git 以命令输出为准**：`git status --porcelain` / `git diff --stat` 为空即工作区干净，
   编辑器的高亮差异可能只是行尾（CRLF/LF）显示差异。

## 八、协作与工程习惯

- **改动范围**：`.c` / `.h` 只改 `User/` 内的文件，`User/` 之外一律只读（见编码规范 01.1）。
- **缩进**：统一 4 个空格。
- **替换实现**：旧写法以注释保留、新代码生效，便于对照回退。
- **只改需求涉及的行**，不擅自增删注释或解除注释掉的代码。
- **提交习惯**：原地覆盖 `main` 分支（不新建分支），需要把零散改动并入上一版时用
  `git commit --amend --no-edit` + `git push --force-with-lease github main`。
- **更新日志**：只记与上一版的核心差异，一句话一条，不写细节。
