# 8. 持久化、调试与整改建议

> Flash 持久化模式、调试输出约定，以及归纳源码时发现的现存风格差异。

## 8.1 Flash 持久化

- 采用“魔数 + RAM 镜像 + 整块擦写”模式：
  - 固定数据区地址与块大小 `#define`，块大小为擦写对齐倍数；
  - 用魔数判断是否为首次写入；
  - 所有 `Set` 只改 RAM 镜像 `buf`，`Save` 才真正擦写 Flash；
  - `buf` 用结构体视图访问，避免手算偏移，并保留 `reserved` 自动补齐。

```c
typedef struct
{
    uint32_t magic;                                     // 魔数
    uint32_t cal[ADC_DEV_NUM][ADC_CAL_POINTS];          // 标定参数表
    float    rate[ADC_DEV_NUM];                         // 单点标定倍率
    uint8_t  reserved[MYFLASH_BLOCK_SIZE
                      - sizeof(uint32_t)
                      - (ADC_DEV_NUM * ADC_CAL_POINTS * sizeof(uint32_t))
                      - (ADC_DEV_NUM * sizeof(float))];
} MyFlashParamTypedef;
```

- 外部数据本体通过指针传入，模块内不持有业务数据。
- **魔数必须与数据布局绑定**：`ADC_DEV_NUM`、`ADC_CAL_POINTS` 或 `MyFlashParamTypedef` 的布局
  一经变化，必须同时更换一个该板历史上**从未用过**的魔数，或改用「魔数 + 布局版本号」双字段校验。
  仅凭魔数精确判等无法识别布局变更：旧布局数据会被误判为「有效」直接加载，新布局再去读偏移已变的
  字段（如 `rate`），就会落到 `memset` 填充的 `0xFF` 区，按 IEEE754 解释即 **NaN**，进而污染整条换算链路。
  - 魔数是**精确 32 位相等**比较，不存在「数值相近更容易命中」；撞车只说明该精确值历史上确实写过 Flash。
  - 换过的值不要再改回去；想恢复默认也可直接擦除数据区。
  - 排查手段：在 `Cal_Init()` 之前打印 `printf("flash magic = 0x%08X\r\n", *(volatile uint32_t *)0x0800FC00);`
- **标定值与实时值必须同源**：零点、标定表与实时采样必须走同一套解码 / 换算规则。
  若零点是用旧规则（例如未做符号扩展）记录的、实时值用新规则，两者相减会得到无效的大数。
  解码规则变更后，应重新标定或重新采集零点。

```c
#define MYFLASH_MAGIC   0x123456A5   /* 布局变更时务必同步更换，且不可改回历史值 */
```

## 8.2 调试输出

- 统一经 `debug.h` 的 `printf`，行尾一律 `\r\n`，输出中文提示便于串口助手阅读：

```c
printf("MyFlash: 擦除失败, status=0x%X\r\n", state);
printf("请放置 %s 砝码，等待稳定...\r\n", steps[i].name);
printf("击中靶子%d,{力度}%f\r\n", pRun->TargetNum, PeakForce);
```

- 大量调试打印默认以 `//` 注释保留，需要时再放开，避免影响实时性。

## 8.3 现存不一致与整改建议

以下为归纳源码时发现的风格分歧，新增代码请以本规范为准，改动旧代码时顺带对齐：

| 项 | 现状 | 建议 |
| --- | --- | --- |
| 缩进 | 统一 4 空格（`main.c` / `HCT6521.c` / `HCT6521.h` / `SM16028E.h` / `GameLogic.h` / `PunchDetect.h` 的 Tab 与 2 空格缩进已于全量复审中统一） | 保持 4 空格 |
| 头文件保护宏 | 统一 `__NAME_H`（`Key.h` 已由 `__KEY_H__` 改为 `__KEY_H`） | 保持 `__NAME_H` |
| 返回值注释 | 统一 `@retval`，不再使用 `@return` | 保持 |
| static 变量前缀 | 状态变量用 `s_`；参数数组 `AdcDeviceParam` / `PunchDeviceParam` / `SM28DeviceParam` / `WeightInfo` / `FilterInfo` **不加** `s_` | 按上述分类保持一致 |
| 模块头注释 | 大模块均有文件头 | 新增模块照此补全 |
| `#include` 顺序 | 统一为：自身 `.h` → 项目头 → 库头 → 标准库 | 保持 |

## 8.4 常见陷阱（实测已踩过）

以下问题均在本工程调试中真实发生过，改动相关代码时务必对照自检。

| 陷阱 | 现象 | 规避方式 |
| --- | --- | --- |
| 魔数撞车 | 布局变更但魔数未换 → 旧 Flash 数据被误判有效 → 重量全为 NaN | 布局变更同步换魔数（见 8.1）；先打印魔数确认当前值 |
| 数组初始化不全 | `static const float arr[ADC_DEV_NUM] = {1.0f};` 只有第 1 个元素为 `1.0f`，其余按 C 规则补 0；`Weight_GetValue = WeiValue * Rate` 使第 2~6 路重量恒为 0 | 默认参数表必须显式写满全部元素，个数与 `ADC_DEV_NUM` 一致 |
| 24 位补码未扩展 | 负值被当成 1600 万量级的大数，破坏零点相减与差分 | 按 [06 原始数据解析](06-数据结构与接口设计.md#63-原始数据解析) 做符号扩展 |
| 时钟认知偏差 | 以为“检测不到外部晶振会自动切回内部晶振”，实际是 HSE 等待超时后**不切换**，SYSCLK 一直保持 HSI 8MHz；静态 `SystemCoreClock` 仍是 72000000 | 保留 `main()` 开头的 `SystemCoreClockUpdate()` 并置于 `Delay_Init()` 之前（见 [1.5 系统时钟与时基](01-总体原则与工程组织.md#15-系统时钟与时基实测结论)） |
| 时基按 72MHz 估算 | `Timer2_Init(800, 10)` 在 8MHz 下实际约 1.10ms，而非注释所写的 1ms，连锁使节拍、超时、运行时间打印都偏大约 10% | 定时器参数按「TIM2 时钟 = 8MHz」换算（见 1.5） |
| 读值异常先怀疑换算 | “放上砝码后重量逐渐上升”曾被怀疑是换算逻辑问题；实际 `Weight_Update` 是无状态纯映射、`Filter_AdcFilt` 原样透传，换算不可能产生渐变 | 用链路分层定位：先放开 `{AD%d}` / `{Filt%d}` 打印，确认是**原始 ADC 在爬**还是后级在爬；再区分物理蠕变与温漂、Σ-Δ 滤波器建立时间、读取时序三类原因 |
| 非阻塞的错觉 | `SM28_Update` 名字像“刷新一下”，实际一帧 138 字节按位翻转 GPIO，8MHz 下约 9ms 全程占 CPU | 见 [7.4 阻塞式外设与主循环占用](07-状态机与中断规范.md#74-阻塞式外设与主循环占用) |
| 工程文件 FileType 错误 | 在 Keil 里手工新建的 `.c` 被当作文本文件（`uvprojx` 中 `<FileType>9`），不参与编译；其它文件一旦调用其函数即**链接报错** | `.c` 必须为 `FileType 1`、`.h` 为 `5`；改 `uvprojx` 前先关闭 Keil，避免被其内存版本覆盖写回 |

```c
/* 正确写法：每个元素都要写出初值 */
static const float s_defaultRate[ADC_DEV_NUM] = {
    /* AdcDevNum0  AdcDevNum1  AdcDevNum2  AdcDevNum3  AdcDevNum4  AdcDevNum5 */
       1.0f,       1.0f,       1.0f,       1.0f,       1.0f,       1.0f,
};
```
